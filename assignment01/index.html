1. What I built

I started from the solution provided for the class, renamed the solution file to match my GitLab project (YangBenjamin.sln), and made these changes:

  • Graphics static library. Created Engine/Graphics as a Static Library project (no precompiled header), added EngineDefaults.props to all configurations, OpenGL.props to the Win32 (x86) configurations and Direct3D.props to the x64 configurations, and copied in the provided source files. The Direct3D/*.d3d.cpp files are excluded from the x86 build and the OpenGL/*.gl.cpp files are excluded from the x64 build, and the files are organized in Direct3D, OpenGL and Windows filters exactly like the Platform-Specific Code example.
  • My game. Created the MyGame_ folder with the MyGame project, the BuildMyGameAssets project (which depends on ShaderBuilder, UserSettings and AssetBuildExe like the example one) and the Content folder. The new projects have their own GUIDs, the MyGame solution folder is listed first in the .sln so MyGame is the default startup project, and MyGame.props sets GameName to MyGame_.
  • Window caption and icon. The main window is now called Benjamin Yang's Animated Triangle -- Direct3D/OpenGL -- Debug (the platform and configuration are kept at the end), the window class name was changed too, and the window uses the provided EAE gamepad icon (IDI_EAEGAMEPAD) instead of the Visual Studio default icon.
  • Logging. cMyGame::Initialize() logs MyGame initialized and cMyGame::CleanUp() logs MyGame cleaned up using Logging::OutputMessage(), which is what the engine projects use.
  • Animated fragment shader. Copied the standard fragment shader to MyGame_/Content/Shaders/Fragment/animatedColor.shader, added it to AssetsToBuild.lua, and changed both Graphics.d3d.cpp and Graphics.gl.cpp to load data/Shaders/Fragment/animatedColor.shader. The shader computes each color channel as 0.5 + 0.5 * sin(g_elapsedSecondCount_simulationTime + phase) with the phases 0, 2π/3 and 4π/3, so the triangle cycles smoothly through the rainbow and every channel stays inside [0, 1]. The HLSL and GLSL branches use identical math so both platforms look the same.

A project that mentions Graphics:: but does not need a reference

Searching the whole solution for Graphics:: also finds Tools/ShaderBuilder (cShaderBuilder.cpp, cShaderBuilder.d3d.cpp and cShaderBuilder.gl.cpp use Graphics::eShaderType::Vertex and Graphics::eShaderType::Fragment). These are enumeration values declared in a Graphics header. An enum is fully defined in the header, so the compiler has everything it needs and the linker never has to look for a symbol inside Graphics.lib. A reference (a link-time dependency) is only required when a project calls a function whose body lives in one of the other project's .cpp files. The same is true for Engine/Application/iApplication.h, which only names the Graphics::sInitializationParameters struct type; it is the .cpp files of Application that actually call Graphics functions, which is why Application (and only Application) needed the reference.

I also checked the reverse direction. Assets, Results and ScopeGuard only contain an Empty.cpp, so even though Graphics includes their headers it does not need a reference to them; everything it uses from them is inline or a template. Graphics does need External/OpenGlExtensions because sContext.gl.cpp calls OpenGlExtensions::Load(), which only the x86 link would have caught.

4. Thoughts about the engine code base

Organization

The engine is split into many small static libraries (Application, Asserts, Concurrency, Graphics, Logging, Math, Time, UserInput, …) that each own one responsibility, plus Tools for the asset pipeline and External for third-party code. Three property sheets (EngineDefaults, Direct3D, OpenGL) hold all of the shared build settings, so an individual .vcxproj contains almost nothing but its file list and references. I like that the platform-specific code is separated by file name (.win.cpp, .d3d.cpp, .gl.cpp) and by folder rather than by giant #ifdef blocks, and that the same engine builds two games (ExampleGame and MyGame) by just changing one macro (GameName) in a props file. The thing I like least is that a lot of the structure lives in Visual Studio metadata (GUIDs, filters, per-configuration ExcludedFromBuild flags, solution-level dependencies for the asset build) that is easy to get subtly wrong and that only shows up as a linker error or a missing data/ folder much later.

Code style

The code is very consistent: c-prefixed classes (cShader), s-prefixed structs (sContext), i_/o_/io_ parameter prefixes, results are returned as cResult values that must be checked rather than exceptions, and there are long comments that explain why something is done and not only what. That makes the code base read like documentation, which is great for a class. On the other hand the tab-indented, heavily commented style makes files long, and some names are very verbose (WaitUntilDataForANewFrameCanBeSubmitted). I would not choose that style for my own hobby project, but I can see that it prevents ambiguity when many students work on the same code.

What confused me

  • At first I did not understand why the game could not find its shaders even though they were in MyGame_/Content. The answer is that the executable reads the built data/ folder inside $(GameInstallDir) (temp/…/MyGame_), which is produced by the BuildMyGameAssets project through AssetBuildExe and ShaderBuilder; the source content folder is never read at run time. Once I traced the AssetsToBuild.lua → AssetBuildExe → ShaderBuilder → data/ chain the whole pipeline made sense.
  • It was not obvious how the Windows libraries (d3d11.lib, opengl32.lib, …) get linked, because the property sheets deliberately set AdditionalDependencies to empty. The engine instead force-includes Windows/ExternalLibraries.win.h in every project, and that header uses #pragma comment(lib, …). My Graphics project needed the same ForcedIncludeFiles setting as the other engine projects; without it the game project failed to link.
  • Creating MyGame by copying ExampleGame's files is tricky because a solution must not contain two projects with the same ProjectGuid, and the "Resource Files" filter needs its own UniqueIdentifier. I also learned that the icon .ico files must be copied as binary files; a corrupted copy makes the resource compiler fail with "old DIB in eaeGamePad.ico".

5. Expectations for the class

After the first lecture I expect this class to be less about writing a lot of gameplay and more about understanding how a real engine is structured: build systems, platform abstraction, asset pipelines, and the discipline of keeping two graphics APIs behaving identically. The assignment already shows that: most of the work was about dependencies and project setup rather than the shader itself.

Personally I want to get a solid mental model of the modern graphics pipeline (vertex/fragment shaders, constant buffers, render state) on both Direct3D and OpenGL, and to learn how the asset build pipeline can be extended to meshes, materials and eventually a Maya exporter. I am interested in tools and rendering, so I hope to come out of this class comfortable enough with engine internals that I can read a commercial engine's renderer and understand the decisions behind it, and confident enough with Visual Studio's build system that project setup is never the scary part of a project again.
